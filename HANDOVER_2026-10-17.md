## The one unresolved fault

Selecting the LED Display page resets the ESP32. Everything else is stable.

## Current evidence (all from the user's testing, not from reasoning)

|---|---|

| Moving Dot running | Did not reset (but see the Speed bug below) |

the LED Display page, and the page's request arrives while a display is running.

## Already eliminated — do not re-tread these

- My tail change — reverted, it still crashed. The tail is innocent.
- Memory corruption from the renderer — `setLed()` already guards its index; a bad index is
  dropped, not written. (This is also why the strips "went dark" — indexes were simply ignored.)
- Out-of-range positions — now clamped both ways on every write; still crashed.
- Bus/CPU saturation — the Chase's draws were capped at 5 ms/200 fps; still crashed. And
  Explosion was animating at 0.5 s/step, i.e. almost not at all.
- ODF chain exhaustion — `chainForBand()` falls back to chain 0 safely, and the heartbeat's
  `cap=0` proves it never fired.
- The scalars in the parameter handler — all go through `jsonNumF`/`jsonNumI` or a `| default`
  on a genuine bool; beat sensitivity is clamped.

## Where to pick up — the one experiment that splits the search

- **Safe** → the crash needs a running display plus that request: an interaction between the
  request path and the render/step loop. Instrument that interaction.

## Prime suspect in code

The LED branch of `handleLiveTweak()` — the colour array (the page sends
`colour: colourRefLED.slice()`) and the VU/EQ parameter set. An array written past its end
while parsing the request is exactly the signature of the RTC-garbage reset. Instrument it
(log the request body / the array length before use) before changing anything.

## Second confirmed bug, smaller but real

Speed means different things to different patterns, but the value is shared.

- Dot family: seconds per step. Chase: LEDs per second (1–50).

Consequence: a Chase Speed of 20 becomes 20 seconds per step for Moving Dot or Explosion. This
is why both "run very slowly" now — the user has confirmed it with both patterns,
independently.

Fix: when the pattern changes, rescale Speed into the new pattern's range with a sensible
default (page-side, in `applyParamRanges`).

# APPENDIX — session 2, found by reading the code (NOT part of the handover above)

## The reset reason, and why the first attempt was void

The handover never records `esp_reset_reason()`. That number splits the search:

| reason | meaning |
|---|---|
| 1 | POWER_ON — a real supply interruption. Also wipes RTC, which explains every "garbage" reading |
| 2 | EN pin |
| 3 | SOFTWARE — `ESP.restart()`; the heap-floor guard is the one that fires from stage 1 |
| 4 | PANIC (firmware crash) |
| 6 | TASK_WDT |
| 9 | BROWNOUT |
| 11 | USB (what an upload / opening the serial port leaves behind) |

Attempt 1 counted the flashes after the user had power-cycled the board themselves, so it
reported 1 = POWER_ON and said nothing about the fault. Attempt 2, pressing LED Display, gave
4 flashes — and that is AMBIGUOUS, because IO48 carries three different signals:

- 3 fast power-up flashes on every boot (`powerUpSequence()`, 200 ms);
- command blinks, 150 ms, immediate: 1 = /live-tweak, 2 = /calibrate-test, 3 = /theme-preview,
  **4 = /init-off** — and leaving the Patterns tab for the LED Display page fires `/init-off`
  at exactly that moment (`index.h:1131-1133` -> `handleInitOff()`);
- the boot report of the previous reset reason, 400 ms, starting 1.5 s in — which was
  **cancellable** (`if (statusBlinks > 0) bcLeft = 0`).

So "4 flashes" was either `/init-off` (no reset at all) or a PANIC (real reset). Fixed in this
build: the report now starts with a 1 s marker flash, blinks at 500 ms, and owns IO48 until it
finishes.

## Two inferences in the handover that do not survive a code read

1. **`prevStage=1` does not point at another task.** `dbgStage` is written ONLY by `loop()` and
   `runLEDPattern()` (and cleared in `setup()`); `webTask()` never touches it. The `/diag`
   legend claiming "1 = web server, 5 = timeline, 9 = brightness save" is fiction — 5 and 9 are
   never written anywhere. Stage 1 is the TOP OF `loop()`, which is also exactly where the
   heap-floor guard sits (`if (ESP.getFreeHeap() < 15000) { logAppend("HEAP FLOOR: …");
   blankDisplays(); ESP.restart(); }`) — so stage 1 + reason 3 means "it leaked and restarted
   itself", and there would be a `HEAP FLOOR:` line in `/log.txt`.
2. **"RTC garbage = a memory overwrite" is not supported.** RTC memory is lost on a POWER_ON
   reset (and on any reset that clears the RTC domain), so garbage in `prevUp/prevStage/prevHeap`
   is the *expected* signature of a supply interruption. The boot counter lives in RTC as well,
   so "BOOT #2" follows from a power cycle rather than proving a crash. Nothing here shows
   firmware wrote outside a buffer.

## Requests the page sends on its own (so "the LED page's request" is not unique)

- `/calibrate-stop` on **every** tab switch except Colours (`index.h:1147`), which blanks
  **unconditionally** (`handleCalibrateStop()`) even when no test was ever running.
- `/init-off` when leaving the Patterns tab (`index.h:1131-1133`) — `displayActive = false`,
  `blankReq = true`.
- `/diag` every 3 s, 1 s while a show plays (`index.h:3113-3116`) — from EVERY page.
- Sliders/checkboxes send `/live-tweak` (section LED) — the only LED-page-specific traffic, and
  it is sent by a *user action*, not by opening the tab.

Consequence: "a request arrives while a display is running" is the steady state, not a property
of the LED page, and navigation alone can darken a running show.

## Two real bugs found while reading (neither is proven to be the reset)

1. **`handleLiveTweak()` has no 240V branch.** Its 240V assignments (`activePattern240V = id`,
   `speed240V`, `quantity240V`, `freq240V`, `mult240V`, `music240V`, `attack240V`, `decay240V`,
   `wrap240V`, `invert240V`) sit INSIDE `if (section == "LED")`. So an LED tweak overwrites
   every 240V global (`speed240V` = Speed in LEDs/s, which `run240VDisplayPattern()` then reads
   as seconds per step), and a 240V tweak sets nothing but the global beat sensitivity. The
   code's own comments assume the branch exists. `git blame` puts it in 3a94152 (2026-10-14);
   `git log -S 'if (section == "240V")'` matches no revision, so no baseline ever had it.
2. **`handleCalibrateStop()` blanks even with nothing to stop**, so a tab switch kills a show.
   The fix is to blank only when `previewMode != 0`.
